# Benchmark results — 2026-09-28

Machine: MacBook Pro Mac16,5, Apple M4 Max, 14 cores (10 performance + 4 efficiency), 36 GB unified memory.
OS: macOS 26.6.2 (25G83).
Go: go1.26.1 darwin/arm64.
Each reported value is the median of 5 runs with -benchtime=1s and -benchmem.

## End-to-end Unmarshal

| Size | yaml.v3 runtime | yamlvalidator runtime | yamlvalidator generated | yaml.v3 generated hook |
| --- | ---: | ---: | ---: | ---: |
| small | 19.3 µs | 33.6 µs | **31.6 µs** | 31.1 µs |
| medium | 189 µs | 345 µs | **334 µs** | 332 µs |
| large | 1.094 ms | 2.065 ms | **2.030 ms** | 2.029 ms |

Against the validated runtime path, generated Unmarshal reduces median wall time by about 5.8% / 3.2% / 1.7% for small / medium / large. Allocations fall from 556 → 502, 6195 → 5831, and 35038 → 33095 respectively. Generated bytes allocated are slightly higher: roughly 2–3%.

The plain yaml.v3 runtime column is intentionally not semantically equivalent: it performs no yamlvalidate validation.

## End-to-end Marshal

| Size | yaml.v3 runtime | yamlvalidator runtime | yamlvalidator generated | yaml.v3 generated hook |
| --- | ---: | ---: | ---: | ---: |
| small | 14.6 µs | 50.3 µs | **49.5 µs** | 31.0 µs |
| medium | 176 µs | **516 µs** | 530 µs | 371 µs |
| large | 0.912 ms | **3.028 ms** | 3.163 ms | 2.112 ms |

The source-aware high-level Marshal path is effectively at parity: generated is ~1.6% faster on small and ~2.8% / 4.4% slower on medium / large. It also allocates about 3–7% more. The reason is architectural: high-level Marshal serializes the generated node, reparses the exact emitted YAML, then validates it so diagnostics can point into the returned bytes.

The standard yaml.v3 generated hook validates the generated node directly and is therefore much faster than yamlvalidator's reflective validated Marshal: approximately 38% faster on small, 28% on medium, and 30% on large.

## Isolated yaml.Node codec

| Operation | small | medium | large |
| --- | ---: | ---: | ---: |
| runtime node decode | 3.18 µs | 31.1 µs | 174 µs |
| generated decode | **2.78 µs** | **25.7 µs** | **145 µs** |
| runtime node encode | 31.8 µs | 333 µs | 1.883 ms |
| generated encode | **2.35 µs** | **24.6 µs** | **151 µs** |

Generated node decode is about 1.15× / 1.21× / 1.20× faster and roughly halves allocation count on medium and large inputs.

Generated node encode is the strongest result: about 13.5× / 13.5× / 12.4× faster. Allocation count drops from 435 → 91, 4037 → 968, and 22450 → 5470. Allocated bytes are about 5.7× / 7.4× / 9.4× lower.

## Generated schema cache

The first benchmark pass rebuilt the generated schema on every operation. After routing generated plans through the same plan cache used by runtime schemas:

| Operation | small before | small after | improvement |
| --- | ---: | ---: | ---: |
| Unmarshal | 50.4 µs | 31.6 µs | 37% lower |
| Marshal | 69.1 µs | 49.5 µs | 28% lower |

On medium inputs the improvement is ~3–4%; on large inputs the schema construction cost is lost in normal benchmark noise because YAML parsing and validation dominate.

## Interpretation

The generated codec itself is effective. Encoding Go values into yaml.Node is more than an order of magnitude faster than the reflective yaml.v3 node encoder for these models, and typed decoding is moderately faster with fewer allocations.

End-to-end Unmarshal improves only modestly because parsing and native validation dominate as input grows. End-to-end source-aware Marshal cannot currently expose the large codec win because it intentionally reparses the emitted YAML for exact source diagnostics.

This benchmark does not justify a claim such as "yamlvalidator is 10× faster" for complete validated operations. The defensible claim is narrower: generated node encoding is ~12–13× faster in this fixture, generated node decoding is ~15–21% faster, and validated Unmarshal sees a small end-to-end improvement.
